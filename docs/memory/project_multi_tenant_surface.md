After PR #5 (Apr 2026), Stello is a single-deploy multi-tenant SaaS, not a fork-your-own-Vercel project. Step 2 (Stripe + paid signup + landing page) is the planned next phase.

**Data plane:**
- Supabase `items` table with RLS is the sole source of truth. `detail.html` and `app.js` have NO filesystem fallbacks — if Supabase fails, the app surfaces the error instead of serving `_items/*.md` or `index.json`. The fallbacks were removed because in a multi-tenant deploy they would have leaked the owner's items to any visitor.
- `_items/` + `index.json` are now a backup target regenerated by `npm run backup` (gitignored).
- `scripts/verify-supabase.js` (`npm run verify`) is the RLS/bucket safety check — run it after any schema change or key rotation.

**API plane:**
- `server.js` + `serve.sh` are deleted. The only server is Vercel Serverless Functions under `/api/*`, all auth-gated via `authenticateRequest()` in `api/_lib/supabase.js`.
- Local dev (post PR #6): `npm run dev` → `scripts/local-dev.js`, a zero-dep ~135-line Node router that serves static files and routes `/api/:path` to `api/:path.js`, loading `.env.local` for env vars. Reuses `authenticateRequest()` so auth isn't bypassed. `vercel dev` still works but requires a Vercel login even for localhost, which is why `local-dev.js` is the default.
- `scripts/analyze.py`, `enrich.py`, `vision_enrich.py` moved to `scripts/archive/` — fully superseded by `api/capture.js` + `api/enrich.js`.

**Key migration:**
- Running on the new `sb_secret_*` / `sb_publishable_*` key scheme in Vercel.
- Legacy JWT key migration is in-progress; follow-up tracked in BACKLOG.md.

**How to apply:**
- Never propose a code path that reads `_items/*.md` or `index.json` at runtime — that's backup mirror territory. All reads go through Supabase via `Stello.getClient()` (frontend) or `authenticateRequest()` / admin client (API).
- If the user asks about running `analyze.py` / `vision_enrich.py` / `enrich.py`, explain they've been replaced and the archived copies are for reference only.
